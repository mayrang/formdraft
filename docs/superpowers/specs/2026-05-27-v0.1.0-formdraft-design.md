# formdraft v0.1.0 — Design

**Status:** Approved (calibration validated 2026-05-27)
**Date:** 2026-05-27
**Scope:** Production-grade form auto-save + offline survival library for React. Zero runtime dependencies. Replaces the dead leader `react-hook-form-persist` (35k weekly DL, last release 2022-05) and fills the structural gap that no current library covers: persist + restore + server sync + offline queue + multi-tab conflict + status state machine + IndexedDB backend, in one cohesive React-shaped API.

---

## 1. Why this exists

Calibration on 2026-05-27 confirmed the gap:

- **Market leader is 4 years dead.** `react-hook-form-persist` (35k weekly DL, last release 2022-05) is unmaintained. `formik-persist` (Jared Palmer's own package) is 8 years dead. `final-form-persist` is 6 years dead. `react-autosave` does server sync only with no restore. No replacement has emerged.
- **No first-party form-lib auto-save in 2026.** React Hook Form (51.5M weekly), Formik (3.85M), TanStack Form (1.92M), Felte — none ships auto-save. The official answer is "BYO."
- **The 7-feature combo nobody bundles.** Persist, restore, server sync, offline queue, multi-tab conflict, discard on submit, status state machine + IndexedDB backend. Each piece exists in fragments (localStorage native, Workbox for SW-level queue, BroadcastChannel raw); composing them takes ~700–900 LOC of production-grade glue per app. Every SaaS reinvents this.
- **The platform traps AI gets wrong.** `navigator.onLine` lies on captive portals. `BroadcastChannel` `structuredClone` silently drops class prototypes. Mobile Safari suspends `online` events on tab background. `react-hook-form-persist` cannot use IndexedDB because its storage interface is synchronous. AI-generated code reliably trips each of these traps.

The result: thousands of React apps ship forms where a refresh loses 20 minutes of typing, an offline save silently fails, a second tab overwrites the first tab's draft, and the "Saved Xs ago" indicator is hand-rolled (often inconsistent) per project. `formdraft` exists to be the library where those gaps are filled once.

---

## 2. Goals and non-goals

### Goals

1. **Single React hook `useFormDraft`** that wraps form state with all 8 core behaviors below.
2. **Zero runtime dependencies.** Native `localStorage`, native `IndexedDB`, native `BroadcastChannel`, native `online`/`offline` events. Only peer deps (React, optionally react-hook-form, optionally zod).
3. **Bundle target ≤ 8 KB gzipped** for the core. Enforced in CI.
4. **First-class React Hook Form integration** via `useFormDraftRHF` adapter (RHF is 51.5M weekly — the dominant form lib).
5. **Schema-first restore.** Zod first-class (peer dep), Valibot/Yup pluggable.
6. **SSR-safe.** Works in Next.js App Router without hydration mismatch.
7. **Production-grade demo.** CodeSandbox-hosted signup wizard demonstrating refresh-survival, offline-write, multi-tab warning.
8. **Migration guide** from `react-hook-form-persist` (one-page, copy-pasteable).

### Non-goals (v0.1.0)

- **Other frameworks** (Vue, Svelte, Solid). v0.1.0 is React-only; non-React adapters are v0.2+ via community PRs. The architecture keeps core framework-agnostic to allow future extraction.
- **Full field-level conflict merge UI.** v0.1.0 ships a `conflict` callback + "last-writer-wins with warning" default. Field-merge UI helpers are v0.2.
- **Network heartbeat.** `navigator.onLine` is unreliable (captive portals, airplane wifi). v0.1.0 documents the trap and lets users plug their own detector; native detector is v0.2.
- **Service Worker integration.** No `workbox-background-sync` — too heavy for the form-draft use case. Drafts survive offline via localStorage/IndexedDB; sync queue runs in-page only.
- **Server-side rendering of draft state.** Drafts hydrate on the client only (client-side after mount). SSR-safe ≠ SSR-rendered.
- **Encryption at rest.** v0.1.0 documents the limitation. Sensitive fields should be excluded via `excludeFields` prop. Encryption is out of scope; consumer integrates if needed.
- **TanStack Form / Formik adapters.** v0.1.0 ships RHF only. Other adapters via community PR.

## 3. Public API

### 3.1 Headless hook (the primary API)

```tsx
import { useFormDraft, indexedDB } from 'formdraft';
import { z } from 'zod';

const ProfileSchema = z.object({
  name: z.string().min(1),
  bio: z.string().max(500),
  preferences: z.object({
    newsletter: z.boolean(),
    theme: z.enum(['light', 'dark']),
  }),
});

function ProfileForm() {
  const {
    values,           // current values (typed from schema)
    set,              // set('name', 'Alice') — partial update
    patch,            // patch({ name: 'Alice' }) — multi-field update
    status,           // 'idle' | 'saving' | 'saved' | 'offline' | 'error' | 'conflict'
    lastSavedAt,      // Date | null
    pendingChanges,   // boolean
    error,            // Error | null (most recent sync error)
    save,             // () => Promise<void> — force immediate save
    discard,          // () => void — clear draft + reset to defaultValues
    submit,           // wrapper: on success, calls discard automatically
    onConflictData,   // remote values from last conflict; null if no conflict
    resolveConflict,  // (choice: 'local' | 'remote' | merged) => void
  } = useFormDraft({
    key: 'profile-form',
    schema: ProfileSchema,
    defaultValues: { name: '', bio: '', preferences: { newsletter: true, theme: 'light' } },
    storage: indexedDB(),     // default: localStorage()
    sync: async (values) => {
      await api.saveProfile(values);
    },
    syncDebounceMs: 1500,
    syncRetry: { maxAttempts: 5, initialBackoffMs: 1000, multiplier: 2 },
    multiTab: 'warn',         // 'warn' | 'last-writer-wins' | 'manual' | false
    onConflict: (local, remote) => {
      // optional; if omitted, default behavior follows multiTab setting
    },
    excludeFields: ['password', 'cardNumber'],  // never persisted
  });

  return (
    <form onSubmit={submit(async (values) => { await api.submitProfile(values); })}>
      <input value={values.name} onChange={(e) => set('name', e.target.value)} />
      <textarea value={values.bio} onChange={(e) => set('bio', e.target.value)} />
      <span>{status === 'saved' && lastSavedAt && `Saved ${timeAgo(lastSavedAt)}`}</span>
      <button type="submit">Save Profile</button>
    </form>
  );
}
```

### 3.2 React Hook Form adapter

```tsx
import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { useFormDraftRHF } from 'formdraft/rhf';

function ProfileForm() {
  const form = useForm({
    resolver: zodResolver(ProfileSchema),
    defaultValues: { name: '', bio: '', ... },
  });

  // Wires draft persistence to RHF — no values/set/patch needed; RHF handles state.
  const { status, lastSavedAt, discard } = useFormDraftRHF(form, {
    key: 'profile-form',
    schema: ProfileSchema,
    storage: indexedDB(),
    sync: api.saveProfile,
    syncDebounceMs: 1500,
  });

  const onSubmit = form.handleSubmit(async (values) => {
    await api.submitProfile(values);
    discard();
  });

  return (
    <form onSubmit={onSubmit}>
      <input {...form.register('name')} />
      <textarea {...form.register('bio')} />
      <span>{status}</span>
    </form>
  );
}
```

### 3.3 Cross-component status

```tsx
import { useFormDraftStatus } from 'formdraft';

// In a header / status bar component, separate from the form
function StatusBar() {
  const { status, lastSavedAt } = useFormDraftStatus('profile-form');
  return <span className="status">{statusLabel(status, lastSavedAt)}</span>;
}
```

Uses `useSyncExternalStore` internally; subscribes to a global registry keyed by draft `key`.

### 3.4 `Options` reference

| Prop | Type | Default | Notes |
|---|---|---|---|
| `key` | `string` | required | Unique identifier (used for storage key and BroadcastChannel name). |
| `schema` | `ZodSchema` (or adapter) | required | Used on restore to validate stored draft; invalid drafts are discarded with a console warning. |
| `defaultValues` | `T` | required | Fallback when no stored draft exists or stored draft fails validation. |
| `storage` | `StorageAdapter` | `localStorage()` | See §6. |
| `sync` | `(values: T) => Promise<void>` | — | Called debounced to push values to backend. Omitted ⇒ no server sync (persist-only). |
| `syncDebounceMs` | `number` | `1500` | Debounce window for server sync. |
| `syncRetry` | `RetryConfig` | `{ maxAttempts: 5, initialBackoffMs: 1000, multiplier: 2, maxBackoffMs: 30000 }` | Exponential backoff for retries. |
| `multiTab` | `'warn' \| 'last-writer-wins' \| 'manual' \| false` | `'warn'` | Multi-tab coordination strategy (see §7). |
| `onConflict` | `(local: T, remote: T) => 'local' \| 'remote' \| T` | — | Custom resolver; overrides `multiTab` default. |
| `onSyncError` | `(error: Error, attempt: number) => void` | — | Called on each failed sync attempt. |
| `excludeFields` | `Array<keyof T>` | `[]` | Fields never persisted (passwords, card numbers). Field is still in `values` while typing but cleared on persist. |
| `version` | `number` | `1` | Stored draft schema version. Mismatch ⇒ discard. |
| `migrate` | `(stored: unknown, fromVersion: number) => T \| null` | — | Optional migration function for schema evolution. |
| `disabled` | `boolean` | `false` | When true, the hook behaves as `useState` — no persist, sync, multi-tab. Useful for SSR. |

## 4. Architecture

### 4.1 Module layout

```
src/
  index.ts                          Public re-exports.
  useFormDraft.ts                   Main hook.
  useFormDraftStatus.ts             Cross-component status subscription.
  rhf/
    index.ts                        Public RHF adapter exports.
    useFormDraftRHF.ts              RHF adapter.
  storage/
    localStorage.ts                 localStorage adapter.
    sessionStorage.ts               sessionStorage adapter.
    indexedDB.ts                    IndexedDB adapter (self-contained, ~50 LOC).
    types.ts                        StorageAdapter interface.
  internal/
    registry.ts                     Global Map<key, draftInstance> + subscribers.
    syncQueue.ts                    Offline queue + exponential backoff.
    broadcaster.ts                  BroadcastChannel + LWW + warning protocol.
    statusMachine.ts                State machine (idle ↔ saving ↔ saved ↔ offline ↔ error ↔ conflict).
    schemaValidation.ts             Zod adapter (and pluggable interface for Valibot/Yup).
    debounce.ts                     Tiny inline debounce util.
    safeStructuredClone.ts          structuredClone with prototype-loss warning in dev.
  types.ts                          Public types.
```

### 4.2 Internal lifecycle

```
mount:
  1. Read stored draft from storage adapter
  2. Validate against schema (and version)
  3. If valid: set values = stored. If invalid: set values = defaultValues, log warning
  4. Subscribe to BroadcastChannel for this key
  5. Subscribe to online/offline events

on user input (set / patch):
  1. Update local values immediately (React re-render)
  2. Write to storage (debounced ~50ms)
  3. Schedule sync (debounced syncDebounceMs)
  4. Broadcast change to other tabs (debounced ~200ms)
  5. Update status: idle → dirty (internal state, not status)

on sync timer fire:
  1. If offline: enqueue + status='offline'; do not call sync()
  2. If online: status='saving', call sync(values)
  3. On success: status='saved', lastSavedAt=Date.now()
  4. On failure: enqueue retry with backoff; status='error' after maxAttempts

on online event:
  1. Flush queue: retry pending sync calls in order
  2. Update status accordingly

on BroadcastChannel message:
  1. If remote values differ from local AND local has pendingChanges:
     a. If multiTab='last-writer-wins': adopt remote, fire onConflict callback
     b. If multiTab='warn': set conflict state, expose onConflictData, status='conflict'
     c. If multiTab='manual': fire onConflict, do nothing automatically
  2. Else: adopt remote silently

on submit success:
  1. Clear storage
  2. Reset to defaultValues
  3. Broadcast 'submitted' to other tabs (so they discard too)

on unmount:
  1. Unsubscribe BroadcastChannel
  2. Unsubscribe online/offline
  3. Flush pending storage write
  4. Cancel pending sync (do not flush; consumer can decide via save())
```

### 4.3 Critical correctness rules (the differentiator)

These are the 7 traps that AI-generated form-autosave code reliably falls into. The library encodes them as invariants:

1. **`navigator.onLine` is consulted, never trusted alone.** Sync only fires when actively triggered by the user-side; failures auto-enqueue regardless of `onLine` state. The `online` event triggers a queue flush attempt but the actual fetch determines success.

2. **`BroadcastChannel` postMessage uses `safeStructuredClone`.** Dev-mode wraps `structuredClone` to detect class instances + Dates and warn the consumer. Production strips warnings.

3. **Mobile Safari tab suspension handled.** Both `online` event AND `visibilitychange` event trigger queue flush. Suspension while online ⇒ `visibilitychange` recovery on focus.

4. **Sync storage interface for `localStorage`, async for `IndexedDB`.** Storage adapter normalizes both via the same async `read`/`write` interface. Internal code never assumes sync.

5. **Cross-tab broadcast loop prevented.** Each tab assigns itself a UUID at mount. Outgoing broadcasts include sender UUID; receivers drop their own broadcasts.

6. **Schema validation is lossy-safe.** Invalid stored drafts are discarded with `console.warn`, not throws. Production crashes are unacceptable for form recovery.

7. **Excluded fields stay in memory, never on disk.** `excludeFields` array; values still in `values` during typing but stripped from storage write. On submit, full values (including excluded) go to `sync` / `submit` handler.

### 4.4 Status state machine

```
                   ┌──────────────┐
                   │   idle       │ ◀─────┐
                   └──────────────┘       │
                          │               │
                user input│               │ discard()
                          ▼               │
                   ┌──────────────┐       │
                ┌─▶│   dirty      │       │
                │  └──────────────┘       │
                │         │               │
                │     debounce            │
                │         ▼               │
                │  ┌──────────────┐       │
                │  │  saving      │       │
                │  └──────────────┘       │
                │   │     │      │        │
                │   ✓     ✗      ⚠        │
                │   │     │      │        │
                │   ▼     ▼      ▼        │
                │ saved  error  conflict  │
                │   │     │      │        │
                └───┴─────┴──────┘        │
                                          │
                offline ⇄ (any state) ─── │
                                          │
                submit() ─────────────────┘
```

States visible in `status` field: `idle | saving | saved | offline | error | conflict`. `dirty` is an internal transient state.

The 7 correctness rules above are derived from the 2026-05-27 calibration where each was identified as a trap that:
- React-Hook-Form-Persist falls into (#4: sync-only storage interface).
- BroadcastChannel raw use falls into (#2, #5: structuredClone, broadcast loop).
- Workbox/native-only solutions fall into (#3: mobile Safari).
- `navigator.onLine` patterns fall into (#1: captive portal lies).

## 5. Edge cases handled

These are catalogued as automated tests (Vitest + jsdom). Each maps to a test file:

| # | Edge case | AI failure mode | Our handling |
|---|---|---|---|
| 1 | Refresh mid-typing | Form resets | Mount restore from storage |
| 2 | Stored draft schema changed (added field) | Restore crashes or silently corrupts | Version mismatch ⇒ run `migrate()` or discard with warn |
| 3 | Stored draft fails schema validation | Crashes app | Discard + console.warn + fall back to defaults |
| 4 | Server sync fails (5xx, network error) | Silent fail | Enqueue retry with exponential backoff |
| 5 | Offline write then reconnect | Sync never fires | `online` + `visibilitychange` flush queue |
| 6 | Captive portal (`onLine=true` but no internet) | Stuck "saving" forever | Sync timeout + retry; status reflects actual fetch result |
| 7 | Two tabs editing same draft | Last tab to save wins silently | Multi-tab strategy: `warn` (default) sets `conflict` status |
| 8 | Tab A edits, Tab B submits | Tab A keeps stale draft | Submit broadcasts; Tab A discards |
| 9 | Component unmounts mid-sync | "setState on unmounted" warning | All state updates guarded by `mountedRef` |
| 10 | User puts a `Date` in form values | BroadcastChannel sees `string` after structuredClone | Dev-mode warning; runtime treats as last-writer-wins for that field |
| 11 | Password field included in persist | Plaintext password in localStorage | `excludeFields` strips before write |
| 12 | Excluded field changes ⇒ sync triggers | Excluded value sent to backend | Sync sends FULL values; persist strips. Two different sets. |
| 13 | Storage quota exceeded | Persist fails silently | Catch + status='error' + `onSyncError` fires |
| 14 | Submit fires; sync queue has pending item | Stale data overrides submitted | On submit success, discard + broadcast + queue cancelled |
| 15 | Tab opens with stored draft from v1, code is now v2 | Crash | `version` mismatch + `migrate` if provided, else discard with warn |
| 16 | Conflict callback throws | App breaks | Catch + log + fall back to multiTab default (`warn` or `last-writer-wins`) |

## 6. Storage adapters

### 6.1 Interface

```ts
export type StorageAdapter = {
  name: 'localStorage' | 'sessionStorage' | 'indexedDB' | string;
  read(key: string): Promise<unknown | null>;
  write(key: string, value: unknown): Promise<void>;
  remove(key: string): Promise<void>;
  clear?(): Promise<void>;
};
```

All async — even `localStorage` adapter wraps sync API in `Promise.resolve()`. This normalizes the internal lifecycle (no sync-vs-async branching).

### 6.2 Built-in adapters

- **`localStorage()`** (default) — sync API wrapped. Suitable for forms ≤ 1MB total.
- **`sessionStorage()`** — sync API wrapped. Tab-scoped (draft dies on tab close).
- **`indexedDB()`** — self-contained ~50 LOC wrapper around native IndexedDB. Suitable for forms with large content (markdown bodies, base64 images). One database per app, one object store, key-indexed.

### 6.3 Custom adapter example (Cloud sync to OPFS / Origin Private File System)

```ts
import { useFormDraft } from 'formdraft';

const opfsAdapter: StorageAdapter = {
  name: 'opfs',
  async read(key) { /* user's OPFS read */ },
  async write(key, value) { /* user's OPFS write */ },
  async remove(key) { /* user's OPFS remove */ },
};

useFormDraft({ key, schema, storage: opfsAdapter, ... });
```

Consumer can wire any backend (OPFS, encrypted localStorage, custom encryption, multi-device sync engine).

## 7. Multi-tab coordination

### 7.1 Strategies

| Strategy | What happens on remote change | When to use |
|---|---|---|
| `'warn'` (default) | Sets `status='conflict'`, exposes `onConflictData`, user calls `resolveConflict(...)` | Safe default; lets user decide. |
| `'last-writer-wins'` | Adopts remote silently (or fires `onConflict` if provided) | Sketch / scratch forms; recoverable. |
| `'manual'` | Fires `onConflict` callback; library does nothing automatically | Full custom UI. |
| `false` | Disables multi-tab coordination entirely | Single-tab apps; avoids BroadcastChannel overhead. |

### 7.2 BroadcastChannel protocol

```ts
type DraftMessage =
  | { type: 'values-changed'; tabId: string; values: unknown; ts: number }
  | { type: 'submitted'; tabId: string; key: string }
  | { type: 'discarded'; tabId: string; key: string };
```

- Sender includes its `tabId` (random UUID generated at mount).
- Receivers drop messages where `tabId === selfId` (loop prevention).
- `ts` is sender's `Date.now()`. Last-writer-wins compares timestamps.
- On `submitted`: receivers discard their local draft.
- On `discarded`: receivers also discard (e.g., user clicked "Cancel" elsewhere).

### 7.3 Web Locks API for leader-election (deferred to v0.2)

Multi-tab WebSocket singleton via `navigator.locks` is a frequent request but is **out of scope for v0.1.0**. Consumers needing it use `tab-election` (5.7k DL) alongside formdraft.

## 12. Risks

1. **Calibration says skilled dev can do this in 250 LOC.** Mitigation: pitch the lib at the 80% of devs who don't know `navigator.onLine` is unreliable, `BroadcastChannel` structuredClone trap, mobile Safari suspension. README leads with these traps to surface value.

2. **React Hook Form ships first-party auto-save.** Probability low (8 years of no movement, latest discussions in 2025 unanswered). If it happens, our RHF adapter becomes redundant; headless hook and IndexedDB adapter still differentiate.

3. **TanStack DB / Tanstack Form absorbs this pattern.** Probability medium. TanStack DB's collection coordinator pattern (BroadcastChannel + Web Locks) could expand to form drafts. Mitigation: ship before they do; differentiate on form-specific UX (status indicator, RHF integration, draft-discard-on-submit semantics).

4. **Distribution.** No personal pain from author means motivation may flag. Mitigation: ship v0.1.0 as production-grade in 4-5 weeks (planned scope is tight), then 1-year light maintenance (critical bug fixes only). Honest about not being a viral product.

5. **Maintenance burden of 8 features.** Mitigation: zero runtime deps means no transitive bug chasing. CI enforces bundle size + test coverage to catch scope creep.

6. **`onConflict` API misuse.** Consumers may write callbacks that mutate state during a render. Mitigation: documentation; runtime warning in dev mode if `onConflict` throws.

7. **Browser API quirks** (Safari BroadcastChannel late support, mobile Safari suspension). Mitigation: ship with explicit browser support matrix in README; test in Playwright across browsers; gracefully no-op multi-tab if BroadcastChannel unavailable.
